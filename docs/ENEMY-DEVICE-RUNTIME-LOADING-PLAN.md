# Enemy and device runtime loading

The lightweight client should prepare behavior implementations for the selected
stage, alongside its selected operator implementations. Imported source data and
admission checks remain build-time concerns. Unknown source mechanics continue
to block their stages.

## Execution sequence

1. Compile enemy traits, unit properties and ability parameters into small JSON
   plans from the existing reviewed registry. Reject unsupported values before
   publication. Preserve trait identities, ability order and duplicate instances.
   Compare compiled execution with the current adapters in meaningful battles.
2. Pack those plans into the existing shared enemy-definition components. Keep
   raw source fields for statistics, diagnostics and the synchronous Node tools.
   Validate parameter/plan invariants and preserve every available stage.
3. Separate the shared feature dispatch from the enemy adapter index. Prepare
   only the kinds referenced by the selected stage and its declared spawn
   dependencies. Missing implementations must fail before battle construction.
   Preserve Node's eager compatibility path through a conditional dynamic import,
   following the existing operator runtime pattern.
4. Remove the source feature registry from the ordinary browser import graph.
   Legacy raw snapshots can explicitly prepare compatible plans through a lazy
   compatibility path; generated stage graphs already carry their plans.
5. Apply the same selected-stage preparation boundary to device controller
   modules. Keep the existing compiled device definitions and shared core
   services; migrate family controllers incrementally without changing their
   combat rules or creating duplicate source records/assets.
6. Measure browser module requests and startup payloads on a basic stage and
   stages exercising several enemy/device families. Check stage switching,
   restart, predefined actors, spawned dependencies and retry after load failure.
   Run relevant combat regressions and verify the generated stage graphs.
   Commit and push the checked milestones separately.

The initial audit covers 769 supported database records: 639 ability plans take
58,983 JSON bytes, with no function values or non-finite numbers. Two subsequently
admitted taunt-only records need no ability implementation. The old shared core
and Stronghold helper module remain a separate delivery-size opportunity; this
work does not claim that all common engine code can be omitted from startup.
